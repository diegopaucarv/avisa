# Parche 7 — Contrato de comportamiento de los guardrails G19–G25

**Archivo SQL:** `docs/PARCHE_7_GUARDRAILS_G19_G25.sql`
**Ámbito:** `config.guardrail_contract` (7 filas nuevas).
**Estado:** aplicado y verificado el 2026-11-18 sobre la base viva `avisa-db`.

## Qué se sembró

Siete filas, una por guardrail, con la misma forma que las 18 filas preexistentes
(G1–G18):

- `input_dispara`: objeto JSON pequeño con el valor que **hace fallar** la regla.
- `input_no_dispara`: el mismo caso con solo el valor necesario cambiado para **pasarla**.
- `output_esperado_dispara`: `{"ok": false, "fix": {...}, "msg": "...", "code": "<REASON_CODE>"}`.
- `output_esperado_no_dispara`: `{"ok": true, "msg": null, "code": null}`.
- `severidad`: `block` en las siete.

La fuente normativa es `docs/AVISA_PRODUCE_v10.md` §16.1.quater (G19–G22) y
§16.1.quinquies (G23–G25); el contrato de test es §9.9. No se inventó texto ni
código: los siete reason codes son los que fija v10.

## Tabla guardrail → reason code → severidad

| Guardrail | Regla | Reason code | Severidad |
| --------- | ----- | ----------- | --------- |
| G19 | No reidentificación: un actor nivel 4 no se vincula a nombre o documento sin validación humana; se propone alias | `G19_REIDENTIFICACION` | block |
| G20 | Cita literal: la cita debe existir literalmente en la fuente y los offsets caer dentro del texto | `G20_CITA_NO_LITERAL` | block |
| G21 | Aprobación humana antes de visibilidad: sin `aprobada_por`/`aprobada_en`, la visibilidad queda en `interna` | `G21_SIN_APROBACION` | block |
| G22 | Fuente permitida: solo lista blanca y API oficial o proveedor licenciado | `G22_FUENTE_NO_PERMITIDA` | block |
| G23 | Nivel Alto antes que dato: dato identificable sin base legal ni consentimiento no se escribe | `G23_SIN_BASE_LEGAL` | block |
| G24 | Identidad sintética por defecto: perfil no analista recibe el identificador `ANI-*`, no el nombre | `G24_REIDENTIFICACION_EN_SALIDA` | block |
| G25 | Sin etiqueta penal sin sentencia: exige `sentencia_firme` con `documento_uri`; `bajo_investigacion` no sale a portal | `G25_ETIQUETA_SIN_SENTENCIA` | block |

`block` en las siete obedece a §16.1.quater: estos guardrails «rechazan, no solo
advierten».

## Criterio de los casos negativos

Cada `input_no_dispara` cambia solo la variable que la regla mide, de modo que el
contrato se pueda leer y discutir sin ejecutar el motor:

| Guardrail | Cambio que hace pasar la regla |
| --------- | ------------------------------ |
| G19 | `vinculo_propuesto` pasa de `nombre_civil` a `alias` |
| G20 | `cita_propuesta` iguala `texto_fuente` y `verificada_literal` pasa a `true` |
| G21 | `aprobada_por` y `aprobada_en` dejan de ser nulos |
| G22 | `en_lista_blanca` pasa a `true` y `via` a `api_oficial` |
| G23 | `base_legal` deja de ser nulo (la regla admite base legal **o** consentimiento) |
| G24 | `tipo_identificador` pasa a `sintetico` y `proyecta_pii` a `false` |
| G25 | `tipo_situacion` pasa a `sentencia_firme`, `sentencia_firme` a `true` y `documento_uri` se puebla |

Las claves siguen el vocabulario del sistema donde ya existe: `visibilidad`,
`aprobada_por`, `aprobada_en` (patrón HITL de `core.outbox_integracion`),
`sentencia_firme` y `documento_uri` (v10 §13.6.bis.v10), `offset_inicio`/`offset_fin`
(v10 §9.2.v10), `base_legal` (`core.actor_datos_personales`), `en_lista_blanca`
(v10 §7.5.v10).

## Nota de estado

G19–G25 **ya no están «abiertos pero vacíos»**. El `CHECK` de `guardrail` admitía
G1–G25 desde el parche 6, pero el contrato solo tenía 18 filas; el bloque §6.a de
`PARCHE_6_CIERRE_CUMPLIMIENTO.sql` dejaba ese pendiente explícito. Con este parche
el contrato cubre los 25 guardrails y puede alimentar la suite de §9.9.

## Pendientes para una persona

1. **Implementación, no contrato.** Las siete filas describen comportamiento. No
   existen todavía: el trigger de visibilidad de G21 sobre alertas, la verificación
   determinista de offsets de G20 y la vista que no proyecta PII de G24.
2. **G21 supone columnas que hoy no están.** `core.alertas_tempranas` no tiene
   `visibilidad`, `aprobada_por` ni `aprobada_en`; el contrato las fija antes que
   el esquema, a propósito (§16.1.quater).
3. **G25 supone una tabla que no se crea aquí.** `core.situacion_judicial_restricta`
   está definida en v10 §13.6.bis.v10 y §2.3.bis, pero no existe en la base.
4. **G22 depende de la lista blanca.** El contenido de `fuentes.lista_blanca` en
   `config.parametro` lo siembra otro parche; este fija solo el comportamiento.
5. **Revisión de contenido (OAIPCS + OGTI).** Los ejemplos son realistas y
   coherentes con el dominio, pero el texto de los `msg` y los valores de `fix` son
   una propuesta: conviene que el área dueña de la política los valide.
